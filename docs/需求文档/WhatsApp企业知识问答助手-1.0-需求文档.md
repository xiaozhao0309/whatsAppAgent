## 1. 产品概述

### 1.1 产品定位

面向企业客户的 WhatsApp 智能问答助手。客户在 WhatsApp 中以自然语言提问，系统自动在企业知识库中检索相关内容（RAG），由大语言模型生成准确、带来源的回答，替代以往由员工人工回复的模式。

### 1.2 背景与目标

现状：企业依赖约 3 名员工手动回复数十名客户的咨询，存在响应慢、重复性问题占用人力、非工作时间无人应答等问题。

目标：通过自动化问答覆盖高频、知识库内有明确答案的问题，将人工从重复性咨询中解放出来，专注于复杂问题与高价值沟通。

### 1.3 1.0 成功标准

- 知识库覆盖范围内的问题，**首问命中率 ≥ 80%**。
- **95% 的消息在 15 秒内**收到回复。
- **幻觉率 < 5%**（答案与来源矛盾或无来源编造）。
- **零密钥泄露、零重复回复事故**。

### 1.4 量级假设

- 用户规模：数十名客户（参考现有 3 名员工可覆盖的咨询量）。
- 并发：低并发，单个进程可轻松承载。
- 该量级下采用单副本部署即可满足需求。

## 2. 范围界定

### 2.1 1.0 包含范围

- 基于企业纯文本文档的 RAG 问答。
- 带来源的回答与低置信度拒答。
- 跨天、跨设备的多轮对话。
- 欢迎引导、帮助指令。
- 异常兜底与转人工（通知值班人）。
- 全员开放 + 基础防滥用（限流、消息长度限制）。
- 用户反馈收集（点赞/点踩）。
- 结构化日志与基础健康检查。

### 2.2 1.0 不做（Non-goals）

| 不做项 | 说明 |
|---|---|
| PDF / Word（.docx）解析 | 1.0 仅支持纯文本 `.md` / `.txt` |
| 语音 / 图片问答 | 仅处理文本消息 |
| 多语言 | 以知识库所用语言为准，不做翻译 |
| 双向人工桥接 | 转人工仅通知值班人，不做值班人与客户的匿名双向中继 |
| 工单系统 / 业务写操作 | 不做查工资、提交报销单等写操作 |
| 多租户 | 不做租户隔离 |
| 文档级权限 | 全员可见同一套知识库 |
| 知识库 Web 管理后台 | 通过目录 + 脚本/接口管理 |
| 多副本 / 负载均衡 | 1.0 单进程部署 |
| Redis、Qdrant server 等外部服务 | 会话与向量库均使用本地/进程内方案 |
| 任务队列（Celery/RQ 等） | 不做消息不丢的强保证 |
| Redis / 数据库持久化 | 会话等运行时状态不持久化 |

### 2.3 未来演进方向（非本期承诺）

- 客户量增长后升级为多副本（引入 Redis 存会话/幂等/限流、Qdrant 改 server 模式）。
- 支持 PDF / Word 等更多文档格式。
- 双向人工桥接、值班排班表。
- 知识库管理后台、命中率分析看板。

## 3. 用户与使用场景

### 3.1 目标用户

企业客户（通过 WhatsApp 咨询的外部客户），全员可用，不设白名单。

### 3.2 核心用户故事

- **US-1 直接问答**：客户就一个具体问题提问，机器人基于知识库给出带来源的答案。
- **US-2 连续追问**：客户围绕同一话题连续追问（如"年假几天？"→"那病假呢？"），机器人能结合上下文理解。
- **US-3 跨天继续**：客户隔几天回来追问，只要在 7 天内，机器人仍记得之前的对话。
- **US-4 换设备**：客户在手机和电脑 WhatsApp 上登录同一账号，对话上下文保持一致。
- **US-5 问了知识库外的问题**：机器人明确表示无法回答，而不是编造答案。
- **US-6 需要人工**：客户主动要求转人工，或机器人连续答不上来时，通知值班人员跟进。
- **US-7 新用户上手**：第一次发消息时收到欢迎语和示例问题，知道能问什么。
- **US-8 评价答案**：用点赞/点踩反馈答案是否有用。

### 3.3 边界场景

- 客户 7 天未对话后再次发消息：会话已过期，机器人提示重新开始，不假装记得。
- 客户短时间内大量发送消息：触发限流，提示稍后再试。
- 客户发送超长消息：超过长度上限时提示精简问题。
- 后端服务（LLM / 向量库）异常：客户收到友好的错误提示，不暴露技术细节。
- 知识库为空：提示先导入文档。
- Twilio 重复投递同一消息：系统去重，不重复回复。

## 4. 功能需求

> 优先级：P0 = 必须有（无则不能上线）；P1 = 应该有；P2 = 可以有。

### F1. RAG 问答主链路（P0）

| 编号 | 需求 | 验收标准 |
|---|---|---|
| F1.1 | 检索结果按相似度分数过滤，低于阈值不强行回答 | 问与知识库完全无关的问题时，返回拒答话术，不调用 LLM 编造内容 |
| F1.2 | 回答必须基于检索到的文档片段，并在有来源时附来源文件名 | 每条有效回答末尾标注来源；多条来源全部列出；无来源时显式说明 |
| F1.3 | 答案长度适配 WhatsApp 阅读体验 | 回答长度控制在可配置上限（默认 ≤ 800 字）以内 |
| F1.4 | 知识库无相关内容时使用统一拒答话术 | 拒答话术固定、友好，引导客户换种问法或转人工 |
| F1.5 | 知识库为空时有明确提示 | 未导入文档时提示先导入，而非报错或空回复 |

### F2. 多轮对话（P0）

| 编号 | 需求 | 验收标准 |
|---|---|---|
| F2.1 | 以 WhatsApp 号码（WAID）作为会话唯一标识 | 同一账号在不同设备上发消息，共享同一份会话上下文 |
| F2.2 | 采用 7 天滑动过期：每条新消息将会话存活时间重置为 7 天 | 7 天内有对话则上下文持续保留；连续 7 天无对话后会话自动清空 |
| F2.3 | 只保留最近 10 轮对话 | 超过 10 轮时自动丢弃最早的对话，只把最近 10 轮送入模型 |
| F2.4 | 上下文总长度设上限（默认 ≤ 2000 字符） | 超过上限时按轮次截断，防止 prompt 超长 |
| F2.5 | 支持指代消解 | 能正确理解"它/这个/那…呢/上面说的"等指代前文的追问 |
| F2.6 | 支持手动重置 | 客户发送"重新开始"/"清空"/"新话题"时立即清空当前会话 |
| F2.7 | 会话过期后不假装记得 | 过期后第一条消息收到"已重新开始"的提示，而非基于不存在的上下文乱答 |

**会话存储说明（1.0）**：会话保存在服务进程内存中（带锁的字典），不使用外部数据库、不做持久化。进程重启会清空所有会话，客户需重新开始——1.0 接受此限制。

### F3. 知识库管理（P0 / P1）

| 编号 | 优先级 | 需求 | 验收标准 |
|---|---|---|---|
| F3.1 | P0 | 支持纯文本文档入库（`.md` / `.txt`） | 放入文档目录后可成功检索到其内容 |
| F3.2 | P0 | 重新入库为全量重建 | 重新导入前清空旧内容，避免新旧文档混杂；导入后返回切片总数 |
| F3.3 | P1 | 切片参数可配置 | 切片大小、重叠长度通过配置调整，文档中给出推荐值 |
| F3.4 | P1 | 入库失败可见 | 空文档或读取失败时给出明确提示，不静默跳过 |

### F4. 欢迎与引导（P1）

| 编号 | 需求 | 验收标准 |
|---|---|---|
| F4.1 | 新用户首次对话收到欢迎语 | 无会话记录的号码首次发消息时，收到欢迎语 + 可提问的示例 |
| F4.2 | 帮助指令 | 发送"帮助"/"help"/"菜单"时返回功能说明与示例问题 |

### F5. 兜底与转人工（P0）

| 编号 | 优先级 | 需求 | 验收标准 |
|---|---|---|---|
| F5.1 | P0 | 低置信度兜底 | 检索最高分低于阈值时返回拒答话术，不编造 |
| F5.2 | P0 | 异常兜底 | 检索/LLM/发送等任意环节异常时，客户收到友好提示，错误堆栈记入日志，进程不崩溃 |
| F5.3 | P0 | 主动转人工 | 客户发送"转人工"/"找人工"等指令时触发转接 |
| F5.4 | P1 | 自动建议转接 | 机器人连续 2 次无法回答时，主动提示并可触发转接 |
| F5.5 | P0 | 转交通知值班人 | 触发转接后，将客户的问题与最近对话上下文发送给配置的值班号码（可配备用号码） |
| F5.6 | P0 | 告知客户已通知 | 给客户回复"已通知值班人员，稍后将与你联系"之类的确认 |
| F5.7 | P1 | 非双向桥接 | 1.0 仅做单向通知；值班人不能通过机器人直接回复客户（需自行联系） |

### F6. 用户反馈（P1）

| 编号 | 需求 | 验收标准 |
|---|---|---|
| F6.1 | 回答后提示可评价 | 回答末尾提示客户回复 👍 或 👎 |
| F6.2 | 记录反馈 | 捕获 👍/👎，将反馈连同问题、回答、来源、时间记入日志 |
| F6.3 | 不重复计数 | 同一轮内客户多次发送表情只记一次有效反馈 |

### F7. 全员开放与防滥用（P0）

| 编号 | 需求 | 验收标准 |
|---|---|---|
| F7.1 | 全员开放 | 不设号码白名单，任何能给机器人 WhatsApp 号码发消息的人均可使用 |
| F7.2 | 单用户限流 | 单个号码每分钟发送消息超过可配置阈值（默认 10 条）时，返回"操作过于频繁，请稍后再试"，不调用 LLM |
| F7.3 | 单条消息长度上限 | 超过可配置上限（默认 2000 字符）时提示客户精简问题，不送入处理 |

### F8. 可观测与运维（P0 / P1）

| 编号 | 优先级 | 需求 | 验收标准 |
|---|---|---|---|
| F8.1 | P0 | 幂等去重 | 基于 Twilio 消息唯一标识（MessageSid）去重，Twilio 重试同一消息不产生重复回复 |
| F8.2 | P1 | 结构化日志 | 每条消息记录：请求 ID、脱敏后的 WAID、问题、检索命中数、最高分、是否回答、耗时、是否异常 |
| F8.3 | P0 | 隐私脱敏 | 日志中不记录完整手机号、API Key、Auth Token 等敏感信息 |
| F8.4 | P1 | 健康检查增强 | `/health` 除了表明进程存活，还能反映向量库是否可访问 |
| F8.5 | P0 | 异常堆栈记录 | 所有后台异常通过日志保留完整堆栈，便于排查 |

## 5. 非功能需求

### 5.1 性能

- webhook 收到消息后**立即返回 HTTP 200**（RAG 与回发在后台执行），避免 Twilio 超时重试。
- 95% 的消息从接收到客户收到回复 ≤ 15 秒。
- 单进程可支撑本期用户量级（数十客户、低并发）。

### 5.2 安全与隐私

- 所有 API Key、Token、账号 SID 必须通过环境变量读取，不得硬编码。
- `.env` 不得入库，仅提交 `.env.example` 模板。
- 日志不记录完整手机号、密钥或敏感对话全文。
- 会话数据仅存于进程内存并设 7 天自动过期，不持久化、不外传。
- 客户可通过"重新开始"指令自助清空会话。

### 5.3 可靠性

- 后台处理全链路异常捕获，失败时给客户友好提示而非静默丢失或崩溃。
- 基于 MessageSid 的幂等保证重复投递不重复回复。
- 1.0 接受以下限制（单副本固有）：
  - 进程重启会清空内存中的会话、幂等记录、限流计数。
  - 进程崩溃到自动恢复期间的消息可能需要客户重发（Twilio 会在窗口内重试）。
  - 发布重启期间有短暂中断。
- 建议使用进程守护（如 systemd）在进程异常退出后自动重启。

### 5.4 可维护性

- RAG 检索/生成逻辑使用直接 SDK 调用，不引入 LangChain 等黑盒编排框架，保证每一步可读、可调试。
- 组件职责清晰：向量化、向量库、切片、入库、问答流水线各自单一职责。
- 新增配置项必须同步更新 `.env.example`、配置模块与说明文档。
- 所有关键路径具备可复现的验证方式。

### 5.5 可配置性

以下参数必须可通过环境变量配置，不写死在代码里：

| 配置项 | 默认值 | 说明 |
|---|---|---|
| 会话过期时间 | 604800 秒（7 天） | 滑动 TTL |
| 会话保留轮数 | 10 | 最近 N 轮 |
| 会话上下文上限 | 2000 字符 | 防 prompt 超长 |
| RAG 相似度阈值 | 0.5（默认，需标定） | 低于此值拒答 |
| RAG 召回条数 | 5 | top-k |
| 答案长度上限 | 800 字 | 单条回复上限 |
| 限流阈值 | 10 条/分钟 | 单用户 |
| 消息长度上限 | 2000 字符 | 单条入站消息 |
| 值班号码 | 无（必填） | 接收转人工通知 |
| 备用值班号码 | 空 | 主值班号发送失败时使用 |

> 注：相似度阈值默认值仅为起点，上线前须用真实知识库与典型问题集进行标定。

## 6. 架构与技术约束

### 6.1 部署形态

- **单副本单进程**：使用 FastAPI + uvicorn 单 worker 运行。
- 无负载均衡、无多副本，不引入 Redis / 外部数据库 / Qdrant server。
- 进程内通过后台任务（BackgroundTasks）异步处理问答。

### 6.2 组件构成

```
WhatsApp 用户
     │
     ▼
Twilio（消息收发）
     │  webhook（form 表单）
     ▼
FastAPI 单进程
├── webhook 入口（立即回 200，后台处理）
├── 幂等去重（MessageSid，进程内）
├── 限流（按 WAID，进程内）
├── 指令识别（帮助 / 重置 / 转人工 / 反馈）
├── 会话管理（按 WAID，进程内存，7 天滑动 / 10 轮）
├── RAG 问答流水线
│   ├── 向量化（本地 sentence-transformers）
│   ├── 向量检索（Qdrant 本地文件模式）
│   ├── 相似度阈值判断
│   └── 生成（火山方舟 Ark，OpenAI 兼容接口）
└── Twilio 通道层（回发答案 / 转发值班人）
```

### 6.3 关键数据流

```
入站消息
 → webhook 立即返回 200
 → 后台任务：
   → 幂等检查（MessageSid）
   → 限流检查（WAID/分钟）
   → 指令识别
   → 读取会话历史（WAID）
   → RAG：向量化 → 检索 → 阈值判断 → 拼历史与上下文 → LLM 生成
   → 写回会话（追加本轮，截断 10 轮，刷新 7 天 TTL）
   → 回发 WhatsApp（答案 + 来源 + 反馈提示）
   → 异常 / 连续答不出 → 兜底或转人工
```

### 6.4 技术栈

| 层 | 选型 |
|---|---|
| 语言 | Python 3.10+ |
| Web 框架 | FastAPI + uvicorn |
| 消息通道 | Twilio WhatsApp（官方 SDK） |
| 向量库 | Qdrant（本地文件模式） |
| 向量化 | sentence-transformers（本地模型） |
| LLM | 火山方舟 Ark（OpenAI 兼容接口） |
| 会话/幂等/限流 | 进程内存（标准库字典、锁、定时器） |

### 6.5 未来升级路径

当客户量增长或需要高可用时，可在**不大改业务逻辑**的前提下升级为多副本：

- 会话管理从进程内存替换为 Redis（同时承载幂等与限流）。
- Qdrant 从本地文件模式切换为 server 模式。
- FastAPI 副本改为无状态，前置负载均衡。
- 若需消息不丢保证，再引入任务队列。

本期组件划分已为此预留清晰边界（会话、向量库各自封装，业务逻辑不直接依赖具体存储实现）。

## 7. 转人工方案（方案 A：单向通知）

### 7.1 触发条件

满足任一即触发：
1. 客户发送"转人工"/"找人工"/"人工客服"等指令。
2. 机器人连续 2 轮低置信度拒答。

### 7.2 处理流程

1. 组装通知内容：客户号码（脱敏）、客户最后问题、最近若干轮对话摘要/原文。
2. 通过 Twilio 发送给配置的值班号码；若发送失败且配置了备用号码，则转发备用号码。
3. 回复客户："已通知值班人员，稍后将与你联系。"

### 7.3 边界说明

- 1.0 不做值班人在 WhatsApp 内直接回复客户的中继功能。
- 值班号码为固定单号码（可选配一个备用），1.0 不做按时间排班。
- 值班号码必须在配置中提供，否则转人工功能降级为仅提示客户"暂无值班人员，请稍后再试"并记录告警日志。

## 8. 多轮对话与会话策略

### 8.1 身份与跨设备

- 会话以 WhatsApp 账号（WAID）为唯一键，与设备无关。
- 同一账号在手机、桌面、网页版登录时，命中同一份会话。
- 若多人共用同一 WhatsApp 账号（企业场景少见），会话会共享，1.0 不做隔离。

### 8.2 过期与截断策略

- **过期**：滑动窗口，每条新消息把 TTL 重置为 7 天。
- **截断**：最多保留最近 10 轮；上下文总字符超 2000 时从最早轮次开始丢弃。
- **过期后行为**：会话被清除，下一条消息收到"我已重新开始，方便再说一下你想问的问题吗？"，不基于旧上下文作答。

### 8.3 重置指令

- "重新开始"/"清空"/"新话题"立即清除会话，返回已重置提示。

### 8.4 隐私

- 会话仅存于进程内存，7 天自动过期，不写盘、不备份。
- 客户可随时通过重置指令自助删除。

## 9. 验收与测试要点

### 9.1 功能验收

- [ ] "重新开始"能清空会话。

## 10. 假设与依赖

### 10.1 假设

- 用户规模为数十客户、低并发，单进程可承载。
- 企业知识库内容可整理为 `.md` / `.txt` 纯文本。
- 值班人员有可接收 WhatsApp 消息的号码。
- Twilio 使用 WhatsApp 正式号码（非 Sandbox）面向客户；Sandbox 仅用于开发测试，有 24 小时会话过期等限制。

### 10.2 外部依赖

- Twilio（WhatsApp 消息收发）。
- 火山方舟 Ark（LLM 推理服务）。
- 进程运行环境（Python 3.10+）。
- （可选）公网 HTTPS 地址用于 Twilio webhook 回调，本地开发可用 ngrok。
