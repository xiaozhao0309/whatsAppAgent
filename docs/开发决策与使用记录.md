本文档记录 WhatsApp 企业知识问答助手 1.0 在需求讨论、技术选型和开发调试过程中的**关键决策、踩过的坑和使用方法**，方便后续快速回忆和接手。

## 一、项目一句话

客户在 WhatsApp 里提问 → Twilio 把消息推给**后端** webhook → 后端通过 HTTP 调用 **AI 服务**做 RAG（向量检索 + LLM 生成）→ 后端把带来源的答案回发 WhatsApp。支持多轮对话、拒答兜底、转人工、限流和反馈。

代码采用 **monorepo 双服务**结构（2026-08-13 由单进程拆分而来），方便后端与 AI 两人分工：

| 服务 | 目录 | 端口 | 职责 | 密钥/数据 |
|---|---|---|---|---|
| 后端 backend | `backend/` | 8000 | Twilio webhook、会话、幂等/限流、指令、转人工；HTTP 调 AI 服务 | Twilio 凭据、`ON_DUTY_NUMBER` |
| AI 服务 ai_service | `ai_service/` | 8001 | embedding、Qdrant 检索、LLM 生成、文档入库 | `ARK_API_KEY`、Qdrant 向量数据、知识库文档 |

两服务唯一耦合是 `POST /answer` 的 JSON 契约（见下方第三章）。

## 二、关键决策记录（why）

### 1. 后端单实例单 worker；AI 服务独立但同样本地单实例

- **背景**：早期讨论过「多副本 + Redis 共享会话 + Qdrant server 模式」。
- **决策**：1.0 不引入 Redis/Qdrant server。**后端**以单 worker 运行（会话/幂等/限流都在进程内存）；**AI 服务**独立成一个本地进程，单实例即可。
- **原因**：用户规模是「3 名员工回复几十名客户」，单实例足够；多副本会凭空引入 Redis、Qdrant server 两个组件，属于为假想需求过度工程，违反宪法原则 V（最小化、本地优先）。
- **拆成双服务的原因**：后端和 AI 将由两个人分别维护，拆分后职责、代码所有权、故障边界清晰，密钥也分离（Twilio 在后端，Ark 在 AI 服务）。
- **代价（1.0 接受）**：
  - 后端进程重启会清空内存会话（客户需重新开始）。
  - 任一进程崩溃期间对应能力短暂中断，靠进程守护（systemd）自动拉起 + Twilio 重试兜底。
  - AI 服务不可达时，后端降级为友好错误提示（不崩）。
- **升级路径**：未来用户量上来后，把 `backend/app/session.py`/`guards.py` 的内存实现换成 Redis、AI 服务的 Qdrant 改 server 模式并加多副本即可，业务编排逻辑几乎不动。

### 2. 会话策略：7 天滑动 + 10 轮 + 2000 字符（存在后端）

- 以 WhatsApp 号码（WAID）为会话唯一键——**天然跨设备**（手机/桌面/网页版同一账号是同一个 WAID）。
- 每条新消息把 TTL 重置为 **7 天**；7 天没说话自动清空。
- 只保留最近 **10 轮**，上下文累计超过 **2000 字符**时从最早轮截断。
- 客户发 reset/clear/new 可手动清空。
- 会话存后端进程内存，**不持久化**；过期后不假装记得，提示客户重新开始。
- 每次问答，后端把截断后的 history 通过 `/answer` 传给 AI 服务。

### 3. 全员开放 + 限流，不做号码白名单

- 所有客户可用，不设白名单。
- 防滥用靠单用户限流（默认 10 条/分钟）+ 单条消息长度上限（默认 2000 字符）。

### 4. 转人工用「方案 A：单向通知」

- 触发：客户说 agent/handoff（或中文「转人工」），或机器人连续 2 次答不出。
- 动作：后端把客户问题 + 最近对话上下文通过 Twilio 发给值班号码（可配主号 + 备用号），并回复客户「已通知值班人员」。
- **1.0 不做**值班人直接在 WhatsApp 里回复客户的双向桥接（复杂度高，放 2.0）。
- 值班号码未配置时优雅降级，提示「暂无值班人员」并不崩溃。

### 5. 仅纯文本知识库

- 1.0 只支持 `.md`/`.txt`，不做 PDF/Docx、语音、图片。文档放在 `ai_service/app/sample_docs/`。

### 6. 后端必须单 worker 运行

- 会话/幂等/限流都在后端进程内存，多 worker 各持一份内存会导致状态不一致、重复回复。
- 启动命令固定：`(cd backend && uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 1)`
- **生产不要加 `--reload`**（改代码自动重启会清空内存）。
- AI 服务无内存会话状态，worker 数相对自由，但 1.0 也用单 worker 简单运行即可。

## 三、架构与代码地图

### 服务间契约（唯一耦合点）

```
POST http://<ai_service>/answer
Request:
  {"question": str,
   "history": [{"role": "user"|"assistant", "content": str}, ...]}
Response:
  {"reply": str,
   "sources": [filename, ...],
   "status": "answered" | "no_match" | "empty_kb" | "error",
   "top_score": float | null}
```

另有 `POST /ingest`（重建知识库，返回 `{"ingested_chunks": n}`）和 `GET /health`（返回 KB 点数/可达性）。后端通过 [backend/app/rag_client.py](../backend/app/rag_client.py) 调用，AI 服务在 [ai_service/app/main.py](../ai_service/app/main.py) 实现。只要契约不变，两边可独立改内部实现。

### 运行时数据流

```
客户 WhatsApp → Twilio webhook (form 表单)
  → 后端 /webhook 立即返回 200（同步做幂等检查）
  → 后台任务（同一用户串行加锁）：
      长度校验 → 限流 → 指令识别 → 会话/欢迎
      → HTTP POST 到 AI 服务 /answer（带 history）
      → AI 服务：embed → Qdrant 检索 → 阈值 → LLM 生成 → 返回
      → 后端：拒答兜底/转人工/拼来源 → Twilio REST API 回发
```

| 文件 | 职责 |

| [backend/app/rag_client.py](../backend/app/rag_client.py) | 调 AI 服务的同步 HTTP 客户端（requests），含超时与错误 |
| [backend/app/config.py](../backend/app/config.py) | Twilio/会话/限流/转人工 + `RAG_SERVICE_URL` 配置 |
| [backend/app/channel.py](../backend/app/channel.py) | Twilio 收发消息封装 |
| [backend/app/session.py](../backend/app/session.py) | 进程内会话（TTL/轮数/字符截断/miss 计数/反馈去重） |
| [backend/app/guards.py](../backend/app/guards.py) | 幂等去重、限流、消息长度校验 |
| [backend/app/commands.py](../backend/app/commands.py) | 指令识别（help/reset/agent/反馈/问候，含中英文关键词） |

**AI 服务 `ai_service/`**

| 文件 | 职责 |
|---|---|

`answered`（正常回答）/ `no_match`（低于阈值或无命中）/ `empty_kb`（知识库空）/ `error`。

## 五、本地运行步骤

需要两个终端（可共用一个装了两份 requirements 的 venv，也可各自建 venv）。

```bash
cd whatsAppAgent
source .venv/bin/activate

# 终端 1：启动 AI 服务（首次会预热 embedding 模型）
cd ai_service
uvicorn app.main:app --host 0.0.0.0 --port 8001 --workers 1

# 终端 2：启动后端
cd backend
uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 1

# 终端 3：（联调 WhatsApp）打洞
ngrok http 8000
# 把 https://<ngrok>/webhook 填到 Twilio Sandbox 的 "WHEN A MESSAGE COMES IN"
```

导入/重建知识库（改了 `ai_service/app/sample_docs/` 后必须执行）：
```bash
# 推荐：服务运行时通过后端代理（无需停服，不会有文件锁冲突）
curl -X POST http://localhost:8000/admin/ingest
# 或直接调 AI 服务
curl -X POST http://localhost:8001/ingest
# 命令行（必须先停掉 AI 服务，避免 Qdrant 文件锁冲突）
(cd ai_service && python scripts/ingest.py)
```

快速验证问答（不连 WhatsApp）：
```bash
curl -X POST http://localhost:8000/ask \
  -H "Content-Type: application/json" \
  -d '{"question":"How do I connect to the VPN?"}'
```

健康检查：
```bash
curl http://localhost:8001/health   # AI 服务 + KB 点数
curl http://localhost:8000/health   # 后端 + AI 是否可达
```

跑测试：
```bash
(cd ai_service && PYTHONPATH=. pytest -q)   # 8 个
(cd backend    && PYTHONPATH=. pytest -q)    # 24 个
```

## 六、开发调试中踩过的坑（重要）

### 坑 1：同一个问题被重复回复（最多重复 2~3 次）

**现象演变**：先发现同一条问题回了两遍；修了一次后，又出现「问候 + 抱歉没找到 + 正确答案」三条。

**根因有三层**：

1. **幂等检查放得太晚**：最初把 MessageSid 去重放在后台任务里，Twilio 重试时两个请求可能同时进入处理。
   - 修复：把幂等检查**提前到后端 webhook 同步阶段**（加入后台任务之前）。
2. **并发竞态**：FastAPI 的 BackgroundTasks 跑在线程池，同一用户的两条消息可能同时处理。上一条还在等 AI 服务/没写完会话时，下一条就判定成「新用户」，于是重复发欢迎语，且两条都去检索可能得到不同结果。
   - 修复：给**每个 WAID 一把处理锁**，同一用户的消息串行处理（`_user_lock`）。
3. **「你好/hi」被当成问题做了 RAG**：纯问候语也送检索，可能答非所问。
   - 修复：新增 `greeting` 指令识别，问候只回欢迎语，不检索，并记录这一轮会话避免重复欢迎。

**另外加了**：AI 服务启动时预热 embedding 模型（在其 `lifespan` 里），消除首次请求约 10 秒的加载卡顿（卡顿会放大上面的竞态）。

**排查方法**：看后端 uvicorn 终端日志里的 `sid=` 和 `request_id=`。
- 同一个 `sid` 出现多次 → Twilio 在重试，看幂等是否生效。
- 不同 `sid` 但内容相同 → 是客户/通道真发了多条，或多进程在跑。
- 用 `ps aux | grep uvicorn` 确认后端**只有一个进程**；多个后端进程会各持一份内存，去重和会话都失效。

### 坑 2：相似度阈值需要标定

- 默认 0.5 是折中值：无关问题可能拿到 0.6 左右（偏松），而**叙述体长文档**对口语化问句可能只有 0.4~0.5（偏严，会误拒答，例如员工手册里的 "Can I work from home?"）。
- 当前有**两道防线**：分数低于阈值直接拒答（不调 LLM）；即使分数过了，LLM 自陈「资料里没有相关内容」时也按拒答处理。
- **上线前必须**用真实知识库 + 典型问题集统计分数分布再定值。Q&A 式文档因标题即问题天然高分，叙述体文档可考虑在小节里补问法关键词或适当下调阈值。

### 坑 3：Qdrant 本地文件模式的文件锁

- 本地文件模式同一时刻只允许一个进程持有。
- AI 服务运行时，**不要**另跑 `ai_service/scripts/ingest.py` 写同一个 collection；用 `POST /admin/ingest`（后端代理到 AI 服务同进程内重建）或直接 `POST /ingest`。
- 拆分后这个坑更清晰：Qdrant 完全归 AI 服务所有，后端不碰它。

### 坑 4：AI 服务不可达时

- 后端 `rag_client` 对连接错误/超时抛 `RAGServiceError`；WhatsApp 问答路径有 try/except，会回友好错误话术而不崩。
- 调试用的 `/ask` 接口也已兜底，返回 `status:"error"` 而非 HTTP 500。
- `GET /health` 会显示后端 `degraded` 并带上 AI 不可达的原因——排查时先看这个。

### 坑 5：进程关闭时的 Qdrant 警告

- 测试/退出 AI 服务时偶尔出现 `QdrantClient.__del__ ... sys.meta_path is None`，是解释器关闭阶段的无害告警，不影响功能。

### 坑 6：frozen Settings 不能直接 monkeypatch

- `config.Settings` 是 `frozen=True` 的 dataclass，单测里用 `monkeypatch.setattr(settings, ...)` 会失败。
- 测试里改用 `SimpleNamespace` 整体替换模块级 `settings`（见各 `tests/` 里的写法）。

## 八、后续演进方向（2.0+，本期不做）

- 多副本：后端用 Redis（会话/幂等/限流）做成无状态副本 + 负载均衡；AI 服务用 Qdrant server + 多副本。
- PDF / Word 文档解析。
- 转人工双向桥接、值班排班表。
- 任务队列（消息不丢保证）。
- 知识库管理后台、命中率/反馈分析看板。
- 多语言、语音/图片问答。
