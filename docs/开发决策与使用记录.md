# 开发决策与使用记录

本文档记录 WhatsApp 企业知识问答助手 1.0 在需求讨论、技术选型和开发调试过程中的**关键决策、踩过的坑和使用方法**，方便后续快速回忆和接手。

- 产品需求细节见 [需求文档/WhatsApp企业知识问答助手-1.0-需求文档.md](需求文档/WhatsApp企业知识问答助手-1.0-需求文档.md)
- Spec Kit 规格/计划/任务见 [specs/001-whatsapp-rag-assistant/](../specs/001-whatsapp-rag-assistant/)

---

## 一、项目一句话

客户在 WhatsApp 里提问 → Twilio 把消息推给后端 webhook → 后端基于企业知识库做 RAG（向量检索 + LLM 生成）→ 回发带来源的答案。支持多轮对话、拒答兜底、转人工、限流和反馈。

---

## 二、关键决策记录（why）

### 1. 单副本部署，不上 Redis / Qdrant server

- **背景**：早期讨论过「多副本 + Redis 共享会话 + Qdrant server 模式」。
- **决策**：1.0 采用**单实例单 worker**。
- **原因**：用户规模是「3 名员工回复几十名客户」的量级，单进程足够；多副本会凭空引入 Redis、Qdrant server 两个组件，属于为假想需求过度工程，违反宪法原则 V（最小化、本地优先）。
- **代价（1.0 接受）**：
  - 进程重启会清空内存会话（客户需重新开始）。
  - 单进程崩溃期间服务短暂中断，靠进程守护（systemd）自动拉起 + Twilio 重试兜底。
- **升级路径**：未来用户量上来后，把 `session.py`/`guards.py` 的内存实现换成 Redis、Qdrant 改 server 模式即可，业务编排逻辑几乎不动。

### 2. 会话策略：7 天滑动 + 10 轮 + 2000 字符

- 以 WhatsApp 号码（WAID）为会话唯一键——**天然跨设备**（手机/桌面/网页版同一账号是同一个 WAID）。
- 每条新消息把 TTL 重置为 **7 天**；7 天没说话自动清空。
- 只保留最近 **10 轮**，上下文累计超过 **2000 字符**时从最早轮截断。
- 客户发「重新开始/清空/新话题」可手动清空。
- 会话存进程内存，**不持久化**；过期后不假装记得，提示客户重新开始。

### 3. 全员开放 + 限流，不做号码白名单

- 所有客户可用，不设白名单。
- 防滥用靠单用户限流（默认 10 条/分钟）+ 单条消息长度上限（默认 2000 字符）。

### 4. 转人工用「方案 A：单向通知」

- 触发：客户说「转人工」，或机器人连续 2 次答不出。
- 动作：把客户问题 + 最近对话上下文通过 Twilio 发给值班号码（可配主号 + 备用号），并回复客户「已通知值班人员」。
- **1.0 不做**值班人直接在 WhatsApp 里回复客户的双向桥接（复杂度高，放 2.0）。
- 值班号码未配置时优雅降级，提示「暂无值班人员」并不崩溃。

### 5. 仅纯文本知识库

- 1.0 只支持 `.md`/`.txt`，不做 PDF/Docx、语音、图片。

### 6. 必须单 worker 运行

- 会话/幂等/限流都在进程内存，多 worker 各持一份内存会导致状态不一致、重复回复。
- 启动命令固定：`uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 1`
- **生产不要加 `--reload`**（改代码自动重启会清空内存）。

## 三、架构与代码地图

### 运行时数据流

```
客户 WhatsApp → Twilio webhook (form 表单)
  → FastAPI /webhook 立即返回 200（同步做幂等检查）
  → 后台任务（同一用户串行加锁）：
      长度校验 → 限流 → 指令识别 → 会话/欢迎 → RAG 问答 → 回发
  → Twilio REST API 回发 WhatsApp
```

### 文件说明

| 文件 | 职责 |
|---|---|
| [app/main.py](../app/main.py) | FastAPI 入口，webhook 编排，启动预热，用户级串行锁 |
| [app/config.py](../app/config.py) | 所有环境变量配置的单一入口 |
| [app/channel.py](../app/channel.py) | Twilio 收发消息封装 |
| [app/session.py](../app/session.py) | 进程内会话（TTL/轮数/字符截断/miss 计数/反馈去重） |
| [app/guards.py](../app/guards.py) | 幂等去重、限流、消息长度校验 |
| [app/commands.py](../app/commands.py) | 指令识别（帮助/重置/转人工/反馈/问候） |
| [app/handoff.py](../app/handoff.py) | 转人工：组装上下文 + 发主/备值班号 |
| [app/observability.py](../app/observability.py) | request_id、号码脱敏、结构化日志 |
| [app/responses.py](../app/responses.py) | 所有面向客户的话术文案（改文案只改这里） |
| [app/rag/pipeline.py](../app/rag/pipeline.py) | RAG 主流程：检索→阈值→拼历史→LLM→长度控制，返回 AnswerResult |
| [app/rag/store.py](../app/rag/store.py) | Qdrant 封装（含 count/clear） |
| [app/rag/ingest.py](../app/rag/ingest.py) | 全量入库（重建） |
| [app/rag/chunking.py](../app/rag/chunking.py) | 文档切片 |
| [app/rag/embeddings.py](../app/rag/embeddings.py) | 本地向量化（all-MiniLM-L6-v2，384 维） |
| [tests/](../tests/) | pytest 单元测试（28 个） |

### AnswerResult 状态

`answered`（正常回答）/ `no_match`（低于阈值或无命中）/ `empty_kb`（知识库空）/ `error`。

## 五、本地运行步骤

```bash
cd whatsAppAgent
source .venv/bin/activate

# 1. 导入知识库（文档放 app/sample_docs/，.md/.txt）
python scripts/ingest.py

# 2. 启动（单 worker，启动时会预热 embedding 模型）
uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 1

# 3. （联调 WhatsApp）另开终端打洞
ngrok http 8000
# 把 https://<ngrok>/webhook 填到 Twilio Sandbox 的 "WHEN A MESSAGE COMES IN"
```

快速验证问答（不连 WhatsApp）：
```bash
curl -X POST http://localhost:8000/ask \
  -H "Content-Type: application/json" \
  -d '{"question":"年假有几天？"}'
```

跑测试：
```bash
pytest -q
```

## 六、开发调试中踩过的坑（重要）

### 坑 1：同一个问题被重复回复（最多重复 2~3 次）

**现象演变**：先发现同一条问题回了两遍；修了一次后，又出现「问候 + 抱歉没找到 + 正确答案」三条。

**根因有三层**：

1. **幂等检查放得太晚**：最初把 MessageSid 去重放在后台任务里，Twilio 重试时两个请求可能同时进入处理。
   - 修复：把幂等检查**提前到 webhook 同步阶段**（加入后台任务之前）。
2. **并发竞态**：FastAPI 的 BackgroundTasks 跑在线程池，同一用户的两条消息可能同时处理。上一条还在加载模型/没写完会话时，下一条就判定成「新用户」，于是重复发欢迎语，且两条都去检索可能得到不同结果（一个 no_match 一个 answered）。
   - 修复：给**每个 WAID 一把处理锁**，同一用户的消息串行处理（`_user_lock`）。
3. **「你好」被当成问题做了 RAG**：纯问候语也送检索，可能答非所问。
   - 修复：新增 `greeting` 指令识别，问候只回欢迎语，不检索，并记录这一轮会话避免重复欢迎。

**另外加了**：启动时预热 embedding 模型，消除首次请求约 10 秒的加载卡顿（卡顿会放大上面的竞态）。

**排查方法**：看 uvicorn 终端日志里的 `sid=` 和 `request_id=`。
- 同一个 `sid` 出现多次 → Twilio 在重试，看幂等是否生效。
- 不同 `sid` 但内容相同 → 是客户/通道真发了多条，或多进程在跑。
- 用 `ps aux | grep uvicorn` 确认**只有一个进程**；多个进程会各持一份内存，去重和会话都失效。

### 坑 2：相似度阈值需要标定

- 默认 0.5 偏松：实测中「今天股价多少」这类无关问题也可能拿到 0.6 左右的分数。
- 当前有**两道防线**：分数低于阈值直接拒答（不调 LLM）；即使分数过了，LLM 自陈「资料里没有相关内容」时也按拒答处理。
- **上线前必须**用真实知识库 + 典型问题集统计分数分布，调到合适值（可先试 0.6~0.7）。

### 坑 3：Qdrant 本地文件模式的文件锁

- 本地文件模式同一时刻只允许一个进程持有。
- 不要在服务运行时另跑 `scripts/ingest.py` 写同一个 collection；用 `POST /admin/ingest` 接口（同进程内全量重建）。

### 坑 4：进程关闭时的 Qdrant 警告

- 测试/退出时偶尔出现 `QdrantClient.__del__ ... sys.meta_path is None`，是解释器关闭阶段的无害告警，不影响功能。

### 坑 5：frozen Settings 不能直接 monkeypatch

- `config.Settings` 是 `frozen=True` 的 dataclass，单测里用 `monkeypatch.setattr(settings, ...)` 会失败。
- 测试里改用 `SimpleNamespace` 整体替换模块级 `settings`（见 tests/ 里的写法）。
